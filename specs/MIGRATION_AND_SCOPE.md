# Migration & Scope Decision

Дата: 2026-10-06. Статус: **DECIDED** (рекомендация принята владельцем проекта).

## Вопрос

Master spec v2.0 описывает игру проще, чем текущая Wanderers (release-1.7: 7 фракций, стадии лора, originEvidence, 40 квестов, 6 миссий, 5 финалов, живой shadow-конвейер void_event_engine). Что с этим делать?

## Решение

**v2.0 — целевая архитектура контента и состояния. Wanderers НЕ переписывается. Миграция инкрементальная, контент-фёрст.**

v2.0 — это не «новая игра» и не «переписать всё». Это правила, по которым пишется НОВЫЙ контент и в которые постепенно переводится старый.

## Что это значит на практике

### Сохраняем без изменений (работает, покрыто тестами)

- Игровой цикл Wanderers (route → risk → decision → reward) и его код.
- void_event_engine как рантайм миссий/нарратива; расширение движка — запрещено (спека 0.18, использование only).
- Существующие 40 квестов, 6 миссий, арки, финалы — это контентный фундамент, не legacy.

### Принимаем из v2.0 немедленно (правила для нового контента)

- HARD BLOCKS HB-01..08 — с сегодняшнего дня для любого нового контента.
- Canon Binding (§17): новые id — только из narrative-канона.
- Content Budget (§18): капы действуют; новый тип контента — сначала правка спеки.
- Новые механики v2.0 (delayed_effects, специализации, слухи/верификация, зеркало знаний, locations.json) реализуются как НОВЫЙ контент поверх существующего state, а не как рефакторинг движка.

### Постепенная адаптация (по мере касания, без отдельного проекта)

| Старое | Целевое v2.0 | Когда |
|---|---|---|
| Вложенные state-структуры лора | Плоские ключи (HB-01) | Только при добавлении новых ключей; старые не трогаем |
| 7 фракций в лоре | 3 active + 4 background_only (§18) | При следующем контентном этапе: gameplay-фокус на omnicorp / free_merchants / tidari, остальные — лор |
| originEvidence (5+ ключей) | knowledge-теги knows\_<id> | Новые улики — тегами; originEvidence не расширяем |
| Миссии (старая схема) | quest\_schema §16 | Новые квесты — только по §16; старые 6 миссий живут как есть до rewrite по MISSION_INVENTORY |

### Явно НЕ делаем

- Не переписываем StoryState/Mission model (анти-план бывш. LORE_IMPROVEMENT_PLAN остаётся в силе).
- Не мигрируем существующие сейвы на плоскую модель (сейв-контракт §20 касается новых ключей).
- Не дублируем игру: весь новый контент проходит через существующий runtime + валидатор конвейера.

## Проверка решения

Решение считается ошибочным, и вопрос переоткрывается, если: (а) новый контент не помещается в капы §18 без rewrite старого кода; (б) валидатор конвейера ловит >30% отказов на реальной генерации (тогда правила несовместимы с реальностью и правятся, а не контент).
